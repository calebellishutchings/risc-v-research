Porting record

PicoRVD: original Pico to Pico 2 RISC-V on Windows

The original project is a USB GDB server and SWIO programmer. The port preserves that job while replacing assumptions that were tied to the RP2040, older SDK/TinyUSB integration, and a Linux-centric development path.

Scope verified. The upstream CoreMark checkout was not edited. CH32V003 support is an external port layer and Windows build tooling alongside PicoRVD, keeping the workload source auditable.

The change map

What changed—and why

AreaEvidence of changeWhy it was needed
Board, SDK, and Windows toolchainPICO_BOARD=pico2, PICO_PLATFORM=rp2350-riscv; SDK/VS Code integration is configured for SDK 2.3.0 and the Pico RISC-V toolchain.Selects Pico 2 hardware and its RISC-V cores explicitly, while using the Windows-installed SDK rather than fetching the older 1.5.1 SDK checkout.
USB CDC transporttusb.h, manual tud_init()/tud_task(), direct CDC calls, and the custom tusb_config.h were removed from the normal target. stdio_init_all() and stdio_usb now provide the transport.Uses the SDK 2.x USB framework. USB is kept out of ordinary printf routing so UART logging cannot corrupt GDB packets; the GDB loop still reads and flushes USB one byte at a time.
Connection sequencingStartup waits for stdio_usb_connected(), then delays briefly before probing the target. Two USB-only probe targets were added.Prevents SWIO setup’s blocking behavior from interfering with host enumeration and gives a minimal way to isolate USB setup failures from debugger/SWIO failures.
SWIO timingThe PIO divider changed from fixed 12 to clock_get_hz(clk_sys) / 10,000,000. Reset changed from a loop-count delay to busy_wait_us_32(40).A fixed divider was calibrated for the 125 MHz original Pico. Pico 2 normally runs a different system clock, so the port targets the required 100 ns PIO tick and a clock-independent reset-low pulse safely above the CH32 requirement.
Flash writer on a faster hostTarget-side routines are explicitly 32-bit aligned; each abstract-command invocation is waited for before the next DATA0 write and after the final word. Padding changed from 0xDEADBEEF to erased-flash 0xFFFFFFFF.The Pico 2 RISC-V core must not make an unaligned 32-bit load from the 16-bit routine arrays. The new wait order avoids overwriting/aborting work that the faster host can otherwise outrun, and padding preserves the erased state.
GDB lifecycleGDB detach explicitly resumes the target; SoftBreak::reset() records the halted state; the page bitmap uses a 64-bit shift.Flashing leaves the target halted. Resuming on detach lets freshly programmed firmware actually run and keeps local halt bookkeeping consistent. The 64-bit shift makes high page bits safe.
Startup reliabilityThe packet parser’s static startup self-test is now opt-in with PICORVD_ENABLE_STARTUP_SELF_TEST.A deliberate early fault could occur before main(), preventing USB enumeration and hiding the useful diagnostic path.

Target workflow

CH32V003 build and flashing support

1

Build on Windows

tools/build_ch32v003.ps1 invokes the Pico SDK’s RISC-V GCC with -march=rv32ec_zicsr and -mabi=ilp32e. It also disables GCC’s memset loop-pattern rewrite when compiling CH32V003fun, avoiding recursive replacement of the runtime’s tiny memset.

2

Program through PicoRVD

tools/flash_ch32v003.ps1 uses the bundled RISC-V GDB over PicoRVD’s Windows COM port. Its load operation exercises PicoRVD’s standard GDB vFlash path, compares sections, resets, then detaches.

3

Observe the target

The supplied V1772 notes reserve PD1 for SWIO on Pico 2 GP28 and use PD0 for an external LED. UART output is enabled at 115200 baud on CH32V003fun’s PD5 TX path for the blink and CoreMark firmware.

Design choices

Why the port is structured this way

Keep the device-facing protocol clean

GDB data goes directly through the USB stdio driver; general console text remains on UART. This is a practical boundary: CDC and logging can coexist without interleaving bytes into the remote protocol.

Make timing depend on clocks, not guesses

PIO and reset timings are expressed from the active system clock or microseconds. That is the essential portability correction when a fixed-cycle RP2040 implementation moves to a Pico 2 RISC-V host.

Leave CoreMark recognizable

The benchmark sources in coremark-main are unchanged. The platform glue is confined to picorvd/example/coremark_port, so target behavior can be reviewed without mixing it into the workload.
